# Core Workflow：任务与交付

> 本文件只定义日常任务治理。权限、发布和破坏性外部操作按需读取
> `core/policy.md`；工具命令按 Context Router 读取对应参考，不在这里复制。

## 0. 治理所有权

TheMasterplan 只在自己是当前任务的交付治理所有者时工作。治理所有权属于协议，
不等于一位成员永久拥有任务。多人按同一协议分工或交接不触发退让。

直接使用编辑器、Shell、Git/jj、OpenCode、Codex、ChatGPT、测试或构建工具本身
不构成冲突。若当前上下文明确表明另一个系统已经拥有 worker/session、任务
workspace/worktree/branch、Issue→PR 状态机、CI/review 路由或
merge/release/deploy 生命周期，则：

```text
TheMasterplan: ABSTAINED — external delivery workflow owns this task.
```

`ABSTAINED` 是任务级瞬时状态，不写入 `.themasterplan/state.json`。不要按品牌、
目录名或版本猜测外部所有权，也不要为外部 orchestrator 建兼容层。

## 1. 任务与范围

- 复杂任务：使用 Issue 记录目标、范围、验收条件与排除项。
- 小型低风险任务：可以使用当前会话中的明确人类授权；PR 记录授权来源、目标、
  范围。
- 微小修复快速通道：仅限目标清晰、无范围争议、单文件或极少数同主题文件、
  约 ≤30 行、只涉及文档/配置/测试/注释、不触及核心逻辑或公共接口、不涉及
  持久化数据/部署/发布/远端数据/破坏性操作，并且验证与最终 diff 均正常。
  需要针对该修复的会话内明确授权；不满足任一条件就走普通 PR 路径。
- 无 Issue 时不得伪造编号。
- 实现需要实质扩大范围时，停止并请求新的范围决定。
- 授权可以来自可核验的 Issue/PR 人类决定或当前会话，不必与执行者在同一会话；
  记录来源、决定者、目标与范围。留言、指派和 review 不自动等于执行授权。

### 1.1 团队角色

在任务记录中标明模式（单人/团队）和当前角色，不按账号共享所有权：

| 角色 | 责任与边界 |
| --- | --- |
| 协调人 | 一项任务一位当前协调人，维护范围、依赖、状态与交接；不替代审批权限 |
| 执行者 | 可有多人，各自拥有明确交付单元、文件边界、worktree 和任务 ref；按授权提交/push/PR |
| 独立审阅者 | 团队任务至少一位未实现该交付单元的人复核候选 diff、验证与风险；自审不能替代 |
| 人类决策者 | 按项目角色配置决定范围、merge、release/deploy；协调或执行身份不自动授予此权限 |

单人可以兼任协调与执行；不能把自己标成自己的独立审阅者。团队可由多人及其
Agent 组成，但 Agent 的本地自审/子代理评审不替代项目要求的人类 review。
协调人未参与实现时可以兼任审阅者；所有实际实现者必须列入 Contributors，
不能靠漏记实现者伪造独立性。模式以任务授权/Issue 为准，不通过把团队 PR 改标
solo 绕过审阅；模式转换需有权范围决定者确认，既有审阅义务不被抹除。
各执行者维护自己的任务 ref，不需要一个人代所有人操作 VCS。一个 Agent 会话
内部仍由主代理负责该会话的外部写入；子代理不独立执行外部交付写操作。

### 1.2 并行与集成

- 将可独立验收的单元拆成子任务/PR，记录负责人、文件边界、基线和依赖顺序；
  不要求多人挤在同一 change、worktree 或分支里。
- 同一交付单元/任务 ref 同时只有一个写入者；共享文件、接口或迁移先协调归属。
  不通过覆盖他人修改或抢占 ref 解决竞争。
- 独立单元并行；依赖单元固定上游候选 SHA，明确 stacked PR 的 base 与合并顺序。
  上游变化后复核 diff、复验并重新审阅；未经批准不重写他人或已发布历史。
- 各单元通过不等于集成通过。协调人安排最终集成候选的权威检查，审阅者核对
  组合 diff 与跨单元接口；父任务仅在全部验收条件满足后关闭。
- 团队任务走普通 PR，不能用微小修复快速通道绕过独立审阅或保护规则。

### 1.3 责任交接

交接记录保存在任务 Issue/PR，不写入采用版本的 `.themasterplan/state.json`。
必须包括旧/新协调人、交付单元与写入者、完整基线/候选 SHA、worktree/ref/PR、
现有修改、验证命令与结果、未完成项/依赖、授权来源/限制和仍运行的作业。

新协调人核验实际文件、diff、远端与作业状态，明确接受；旧协调人确认停止该任务
写入后交接生效。旧协调人不可用时，只能由有权人类明确重新指派，核实旧作业已
停止或隔离后接手。日志、意图或一次观察超时不证明作业已经停止。

未接受/未核验前不宣称完成交接；存在两位活跃写入者、未知修改、冲突 ref 或
互相矛盾的决定时停止有风险写入，保留状态并按 Policy 请求有权人类决定。
交接不是授权升级；需要改变执行身份、目标或操作范围时重新审核授权。

## 2. 默认继续与完成

在授权范围内，默认继续完成安全的本地工作：

```text
读取相关文件
实现/编辑
格式化、lint、测试
修复本次改动造成的失败
重跑受影响验证
检查工作区与最终 diff
准备交付材料
```

不要在第一次实现后仅因为“可以让人审阅”而提前结束；以根部 `AGENTS.md`
Completion Contract 为完成定义。

## 3. 工作区、验证与 diff

- 开始写入前确认任务来源、工作区归属和未知本地修改；不覆盖来源不明的修改。
- 一个交付单元对应一个可验证 change/短生命周期任务引用；并行子任务各自隔离，
  父任务记录集成依赖，不混入无关修改。
- 迭代中按改动风险运行受影响验证：文档检查链接与契约，行为修改运行相关测试；
  无法界定影响、跨模块或共享接口改动时扩大验证。无需每次编辑重跑全套。
- 先确认命令的副作用；未知验证入口不等于安全本地测试。涉及真实数据、生产服务、
  部署或远端写入的验证仍遵守项目安全与授权边界。
- push 前对最终候选运行根部 `AGENTS.md` 记录的完整权威验证入口，并阅读完整最终
  diff。相关测试不能代替这道门；修改使验证失效时必须复验。
- 验证失败时，修复由本次改动造成的问题并重跑相关验证；不得把失败或未执行
  的验证表述为通过。
- 基线、任务引用或远端 ref 冲突且正确目标不明确时停止，不猜测、不强推。

## 4. Pull Request 交付

普通 PR 使用仓库 `.github/pull_request_template.md`，让模板与 CI validator
作为机械契约的单一事实来源；不要在 Skill 或其他入口复制字段清单。

创建或更新 PR 后：

- 等待关联 CI；
- CI 因本次修改失败时继续修复并重跑；
- 团队 PR 记录协调人、执行者、独立审阅者、依赖与当前候选；按模板维护协作记录；
- 独立审阅绑定候选 SHA，修改后的候选不得沿用旧审阅；blocking review 未解决时
  不报告可合并，不自行 dismiss 别人的意见；
- CI 通过可以报告验证通过；独立审阅和项目 required reviews 未满足时只能报告
  等待审阅，不能把自审勾选或正文声明当作真实 GitHub 批准；
- 完整检查、独立审阅与项目保护门满足后，再提交有权人类决定是否合并；
- 合并后的 Agent 自建任务分支按 `core/policy.md` §7.1 处理清理。

## 5. 真正的停止边界

以下情况才需要停止并取得人类决定或重新授权：

- 安全、隐私、合规、Secret 或数据风险；
- 任务范围发生实质扩大；
- merge/release/deploy/受保护分支推进缺少所需授权；
- 需要强推、移动/覆盖已发布 Tag、覆盖未知人工修改；
- 远端 ref、候选 SHA 或已批准状态发生冲突/变化；
- 外部交付工作流已拥有当前任务；
- 继续操作将跨越 `core/policy.md` 定义的破坏性或发布边界。

## 6. 卫生与审查

最终 diff 不应包含误删、范围外变更、调试代码、临时文件、缓存或无关生成物。

代码审查意见只使用三类：

```text
合并前必须修复
建议本次修复
可以后续处理
```

每条意见说明具体问题、影响和需要的修复。
