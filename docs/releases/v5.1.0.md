# v5.1.0 发布说明

这是本次发布准备的中文说明。发布状态以 [GitHub Releases](https://github.com/OasisSaber/TheMasterplan/releases) 与 `v5.1.0` 不可变 Tag 为准；这份文件或版本清单本身不证明版本已发布。

## 这次解决了什么

- **多人协作不再挤在一个人手里。** 明确协调、实现、独立审阅和批准的分工。成员分别维护工作区与分支；依赖固定提交；交接须核验并确认旧写入已停止。代理检查不能代替人类审阅或合并、发布授权。见 [PR #96](https://github.com/OasisSaber/TheMasterplan/pull/96)。
- **更新计划不能被随意改写后执行。** 应用时重新生成标准计划并核对来源、完整操作和安装状态；执行器更新也逐文件列入计划。文件快照复查，State 最后写入，遇到可捕获异常尝试安全回滚。见 [PR #98](https://github.com/OasisSaber/TheMasterplan/pull/98)。
- **损坏安装与路径边界更明确。** 必需 Profile 的记录或文件缺失时普通更新停止；State/Plan 的纯路径校验不依赖当前目录。拒绝 Windows 保留名、尾部点或空格，以及大小写别名碰撞；更新与回滚保留适用的既有文件权限。见 [PR #100](https://github.com/OasisSaber/TheMasterplan/pull/100)。
- **按任务读取规则，采用后规则可达。** 入口只路由到必要材料；Git/jj Profile 保留完整依赖闭包，不默认加载无关规则。见 [PR #94](https://github.com/OasisSaber/TheMasterplan/pull/94)。

## 升级时要注意

1. `v5.0.0` 与冻结的 `v1` 都保持原指向，不移动、不覆盖。已有消费者不会自动收到这些变更。
2. 新版本仍兼容既有 State schema v1 和历史执行器登记；但是旧计划不保证可以继续执行。使用新候选执行器重新生成、审阅更新计划，并另行批准应用。
3. 只将旧执行器的 `--source` 改成新包，不能获得新执行器的安全检查。先审核精确候选源码，使用其中的执行器；不要未经批准覆盖本地修补的 `.themasterplan/bin/`。
4. 本地改动、损坏安装、非法路径会安全停止；不要用首次 adoption 命令绕过更新保护。先诊断、备份，再取得明确恢复方案。
5. 更新不会自动同步已有业务仓库的 Actions 或自定义 Issue/PR 模板。中央调用的 `uses` 与 `policy-ref` 必须配对固定到同一 Tag 或完整 SHA。生成模板只在目标不存在时创建，已有配置须由项目维护者审核同步。
6. 中央 Actions 公共输入、权限和检查名称不变；无协作节的历史 PR 继续机械兼容。本仓库自己的 PR 事件要求协作记录，采用者可显式迁移到严格入口，结构通过不证明身份、权限或真实 approval。

完整操作见 [更新指南](../client-update-flow.md)、[Actions 接口](../actions-interface.md) 和 [版本通道](../release-channels.md)。

## 已知限制

- 可捕获异常的回滚不是跨文件崩溃原子事务，也不是 OS 文件锁。断电、强杀和并发写入仍需备份、独占写入与重新诊断。
- Windows 回归通过不等于所有平台的真实采用演练完成；macOS 与 Windows 完整采用仍按采用指南记录实际 smoke。
- 独立代理审阅、CI 和结构校验不替代真实人类审阅、项目权限或发布批准；本次没有配置 Ruleset、成员权限或 CODEOWNERS。

## 发布执行前的门

先合并并验证发布准备 PR，固定最新 main 的完整候选 SHA，核验版本和 Release Notes，完成独立消费者检查和所需人类审阅。人类一次批准完整发布事务后，按协议连续执行：创建并推送 annotated Tag → 真实固定 Tag 消费者 smoke → 创建 GitHub Release（`--verify-tag`）→ 远端对齐验证。

固定 Tag smoke 未通过时不得创建 Release；候选、目标或结果变化时停止并重新审核。不要把发布准备或本说明的存在当作发布完成。
